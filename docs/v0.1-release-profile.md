# PANDA v0.1 Release Profile

**Release:** 0.1.0

**Status:** Complete local release baseline (2026-08-10)

**Scope:** One deterministic, dynamically routed, policy-gated, independently
verified filesystem execution with explicit non-success fixtures and a complete
causal trace.

This profile states what the repository actually supports. It narrows the
conceptual [Framework Requirements](requirements.md) to the executable v0.1
product and must not be read as a production-security or full-framework
conformance claim.

## 1. Runtime profile

PANDA v0.1 is a local TypeScript/Node.js architecture proof. The Fastify daemon
owns one set of process-local stores, capability and connector registries,
policy, coordinator, and effect observer. HTTP resources, the SDK, WebSocket
events, and dashboard read that same state.

The release baseline is:

- Node.js 20 or newer;
- pnpm 9.15.1;
- strict TypeScript targeting ES2022;
- loopback daemon at `127.0.0.1:4317` by default; and
- dashboard development server at `127.0.0.1:5173` by default.

The root package is private. No workspace package is published by this release.

## 2. Supported capabilities

The only capability identity values are:

| Capability | v0.1 implementation |
| --- | --- |
| Perception | Normalizes the accepted file signal and, after Action, independently observes the filesystem effect |
| Analysis | Classifies request readiness, identifies missing information, and verifies observed path/content/byte/hash evidence against Goal criteria |
| Network | Registerable effect-free placeholder; returns a wait because the frozen fixture requires no exchange |
| Decision | Selects the bounded filesystem candidate or safe non-action, records alternatives/evidence/constraints/rationale, and terminates unrecoverable fixture failures |
| Action | Re-evaluates effect policy and dispatches the authorized request through the filesystem connector |

Capability outputs select a typed `NextStep`: invoke any registered capability,
invoke self, wait, or terminate. The coordinator contains no scenario route.
Memory is persistence used by capabilities; planning, understanding, and
reflection are implementation techniques rather than capability identities.

## 3. Supported request and effect

The sole accepted creation request is:

```json
{
  "type": "demo.file.requested",
  "source": "optional-source",
  "payload": {
    "path": "proof.txt",
    "content": "PANDA v0.1 completed"
  }
}
```

`type` and `source` are optional. `payload` is required; `path` or `content` may
be absent so the runtime can record incomplete information and wait safely.
Unknown top-level or payload fields are rejected by the HTTP schema.

The only real effect is:

| Field | Supported value |
| --- | --- |
| Action type | `filesystem.write` |
| Connector | `filesystem` |
| Target | `execution-workspace` |
| Encoding | UTF-8 |
| Maximum content | 65,536 bytes by default |
| Effect result | Exact bytes, byte count, SHA-256, relative/resolved path, policy evidence, and explicit outcome/effect status |

No Network call, process execution, unrestricted filesystem access, repository
mutation, or external service mutation is supported.

## 4. Filesystem sandbox boundary

For data directory `<data>`, execution `<executionId>` writes only below:

```text
<data>/runs/<executionId>/workspace
```

The default data directory is `.panda`. Tests and release validation use
isolated temporary directories outside the checkout.

Policy and connector checks reject:

- unsafe execution identity;
- empty, absolute, Windows-absolute, workspace-root, or traversing paths;
- a target outside the execution workspace;
- symbolic-link path components or targets;
- a regular-file target with multiple hard links;
- an unsupported action, connector, target, or encoding;
- mismatched execution/Goal/correlation context;
- missing policy authorization; and
- content above the configured limit.

The connector creates managed directories, re-evaluates the boundary before
opening the target, uses no-follow semantics where available, restricts file
mode, reports possible partial/unknown effects conservatively, and computes the
actual byte hash. A separate read-only observer resolves and reads the file
again before Analysis verifies the Goal.

This is defense in depth for one trusted local fixture. It is not a container,
virtual machine, operating-system user boundary, disk quota, malware sandbox,
or protection against a hostile process with the same host permissions.

## 5. Durability and restart behavior

`InMemoryExecutionStore` and `InMemoryGoalStore` are the v0.1 adapters.
Executions, Goals, trace records, waits, and subscriptions exist only in the
daemon process and are lost on restart. There is no database, write-ahead log,
checkpoint, replay, reconnect resume token, or crash recovery.

The HTTP list and detail endpoints therefore describe only the current process.
WebSocket delivery is best effort after trace commit; a connected client can
miss events, but the HTTP trace is authoritative while the process remains
alive. Store and coordinator ports permit a future durable implementation, but
v0.1 makes no persistence guarantee.

An operator must treat daemon shutdown as termination of all in-memory work.
Do not use v0.1 where losing work, evidence, or wait state on restart is
unacceptable.

## 6. Status vocabulary

| Domain | Supported statuses |
| --- | --- |
| Goal | `pending`, `active`, `suspended`, `awaiting-human`, `achieved`, `failed`, `cancelled` |
| Execution | `pending`, `running`, `waiting`, `succeeded`, `failed`, `cancelled` |
| Terminal outcome | `succeeded`, `failed`, `cancelled` |
| Action outcome | `succeeded`, `failed`, `rejected`, `cancelled`, `timeout`, `indeterminate`, `partial` |
| Effect | `none`, `attempted`, `completed`, `partial`, `unknown` |
| Policy evaluation | `allow`, `deny`, `require` |
| Transition | `committed`, `rejected` |

Only independent evidence matching every explicit success criterion produces
Goal `achieved` and Execution `succeeded`. Connector dispatch or a
success-shaped Action Outcome alone is insufficient.

## 7. Trace contract

The execution store assigns a consecutive, per-execution sequence to every
record. Each record has a stable ID, schema version, timestamp, execution ID,
Goal ID, correlation ID, producer, category, type, payload, and optional direct
cause. In a complete v0.1 trace, the first Signal is the sole root and every
later cause resolves to an earlier record in the same execution.

Supported categories are:

| Category | Material evidence |
| --- | --- |
| `signal` | Accepted external request |
| `goal` | Explicit Goal creation |
| `goal-status` | Committed Goal state change |
| `capability-invocation` | Capability start/completion and selected `NextStep` |
| `observation` | Normalized input or independently observed effect |
| `assessment` | Readiness or verification evidence and method |
| `decision` | Selected option, alternatives, constraints, evidence, and rationale |
| `transition` | Requested and committed/rejected route change |
| `policy-evaluation` | Transition/effect policy result and reason |
| `action-request` | Exact authorized effect candidate |
| `connector-invocation` | Connector attempt and outcome link |
| `outcome` | Action/effect status, timing, result, and error |
| `failure` | Structured failed operation, category, code, cause, retryability, and effect status |
| `wait` | Reason and optional resume event |
| `termination` | Explicit terminal outcome and reason |

## 8. Public interfaces

### Daemon

- `GET /health`
- `POST /executions`
- `GET /executions`
- `GET /executions/:id`
- `GET /executions/:id/trace`
- WebSocket `/events`

The daemon returns structured `400`, `404`, and `500` errors. It enables
permissive CORS and has no authentication; keep it bound to loopback.

### SDK

`PandaClient` supports `health`, `createExecution`, `listExecutions`,
`getExecution`, and `getExecutionTrace`. `PandaRequestError` preserves the HTTP
status and daemon error detail. The SDK does not provide retry, cancellation,
timeout, or WebSocket helpers.

### Dashboard and CLI

The dashboard creates and lists executions, displays Goal state and criteria,
derives source-linked operator answers, and renders the complete sequence-stable
causal timeline. The CLI provides `init`, `dev`, `daemon`, `dashboard`,
`doctor`, and `version`; it is not an execution-management client.

## 9. Explicitly unsupported production features

- Durable persistence, restart recovery, replay, and automatic wait resumption
- Authentication, authenticated principals, multi-tenant authorization, and
  production network exposure
- General planning/replanning, retries, compensation, or rollback
- Human approval, interruption, override, or resume API
- LLM/model-provider integration, learning, prediction, and anomaly detection
- Real Network transports, service discovery, connector health, or distributed
  execution
- Multiple agents, subgoal scheduling, competing-goal arbitration, or resource
  scheduling
- Plugins, MCP, marketplace, cloud synchronization, Docker deployment, and
  mobile applications
- Metrics, rate limiting, quotas, telemetry export, privacy/retention controls,
  secret management, and emergency stop
- Additional effects beyond the bounded filesystem write
- Production compatibility or migration guarantees for the private packages

## 11. Automated release evidence

`apps/daemon/src/release.e2e.test.ts` executes the required matrix through the
daemon HTTP boundary and canonical runtime assembly:

1. successful sandboxed execution and independent verification;
2. missing-information wait with no Decision or Action;
3. effect-policy denial with no connector invocation;
4. pre-effect connector failure routed to final Decision;
5. verification mismatch that cannot achieve the Goal;
6. invocation-limit structured termination;
7. concurrent execution identity/workspace/trace isolation; and
8. complete HTTP-retrieved correlation and causation reconstruction.

The successful trace also asserts the ordered release gate:

```text
signal accepted
  -> goal created
  -> decision explained
  -> effect policy allowed
  -> action authorized
  -> connector completed
  -> outcome succeeded
  -> effect independently observed
  -> success criteria verified
  -> goal achieved
  -> execution succeeded
```

Focused shared, core, SDK, daemon, and dashboard tests remain the detailed
evidence for contract, safety-boundary, failure, and presentation behavior.
