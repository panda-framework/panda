# PANDA v0.1 Frozen Scope Contract

**Status:** Approved Phase 0 baseline

**Applies to:** PANDA v0.1 implementation and release tests

**Supersedes:** No architecture or normative requirement; this document fixes
the first implementation profile within those constraints.

## 1. Purpose

This document freezes the observable product contract for PANDA v0.1. Later
implementation phases may choose language-level APIs and internal mechanisms,
but they must implement these fixtures and outcomes without turning PANDA into
a fixed loop.

PANDA v0.1 demonstrates one safe, deterministic, model-independent execution
that performs a sandboxed filesystem effect and verifies it independently. It
also demonstrates four non-success paths with no false-positive goal
completion.

## 2. Architectural constraints

The canonical capabilities are exactly:

- `perception`
- `analysis`
- `network`
- `decision`
- `action`

They are dynamically connected responsibilities, not ordered stages. Each
capability result may propose any capability, itself, a wait, or termination.
The routes in this document are acceptance expectations for these fixtures;
they are not a global transition graph or a mandatory loop.

Network must be registerable and selectable, but the filesystem fixtures do
not require an exchange across a trust or ownership boundary and therefore do
not invoke it. Deterministic rules are sufficient for every fixture. No LLM or
model provider is required at runtime.

## 3. Golden-path contract

### 3.1 Input signal

The accepted input is a signal from the acceptance-test source with this
semantic content:

```json
{
  "type": "demo.file.requested",
  "payload": {
    "path": "proof.txt",
    "content": "PANDA v0.1 completed"
  }
}
```

The concrete Phase 1 `Signal` also supplies its stable identity, schema
version, source, receipt time, execution/goal correlation, and provenance as
required by the canonical contracts. Those values are generated per test and
are not fixed literals.

### 3.2 Goal

The execution creates one explicit goal with this objective:

> Create `proof.txt` inside this execution's workspace with UTF-8 content
> exactly equal to `PANDA v0.1 completed`, then independently verify the
> resulting environmental state.

Success requires all of the following:

1. Policy allows the exact effect request.
2. The filesystem connector reports a successful completed effect, not merely
   acceptance or dispatch.
3. A later Perception operation reads the file from the sandbox independently
   of the connector result.
4. Analysis verifies the observed relative path, exact bytes, byte count, and
   SHA-256 content hash against the goal criteria.
5. The goal becomes `achieved` and the execution terminates with outcome
   `succeeded` only after that verification.
6. The complete trace satisfies the identity and causation rules in section 7.

Dispatch, connector acceptance, or a success-shaped connector response alone
must never mark the goal achieved.

### 3.3 Expected dynamic route

```text
Perception -> Analysis -> Decision -> Action
           -> Perception -> Analysis -> terminate(succeeded)
```

Capability outputs select every arrow. The coordinator must not encode this
sequence. Decision records the selected filesystem intent, relevant
alternatives (including no action), decisive evidence, and rationale. Action
executes only after policy approval. The post-action Perception invocation
observes the environment rather than trusting the action outcome.

### 3.4 Expected effect

For execution `<executionId>`, the only created or replaced file is:

```text
.panda/runs/<executionId>/workspace/proof.txt
```

Its bytes are the UTF-8 encoding of `PANDA v0.1 completed` with no appended
newline. The recorded byte count and SHA-256 hash must match those bytes.

## 4. Required non-success fixtures

Every fixture starts a separate execution and goal. Implementations may record
additional diagnostic records, but they must preserve the expected capability
route, effect count, status, and decisive evidence.

| Fixture | Input or injected condition | Expected dynamic route | Connector effects | Final execution / goal |
| --- | --- | --- | --- | --- |
| Missing information | `demo.file.requested` lacks `content` | Perception → Analysis → wait for Perception input | 0 | `waiting` / `awaiting-human` |
| Policy denial | Valid golden input; the effect policy deterministically returns `deny` | Perception → Analysis → Decision → Action → Decision → terminate(failed) | 0 | `failed` / `failed` |
| Connector failure | Valid golden input; filesystem connector returns a pre-effect failure | Perception → Analysis → Decision → Action → Decision → terminate(failed) | 1 attempted, 0 completed | `failed` / `failed` |
| Verification failure | Connector completes, but later observation reports mismatched bytes | Perception → Analysis → Decision → Action → Perception → Analysis → Decision → terminate(failed) | 1 completed | `failed` / `failed` |

The final Decision in each terminal failure fixture records that no safe,
bounded v0.1 recovery remains. More general retry, compensation, or replanning
is outside v0.1 scope.

### 4.1 Missing information

Use this semantic input:

```json
{
  "type": "demo.file.requested",
  "payload": {
    "path": "proof.txt"
  }
}
```

Perception preserves the incomplete input without inventing content. Analysis
identifies `content` as an information need. The next step is `wait`, with a
resume condition for a corrected `demo.file.requested` signal. No Decision
selects an effect, no `ActionRequest` is created, and no connector is invoked.
The execution is waiting and the goal is awaiting authorized input rather than
incorrectly failed or achieved.

### 4.2 Policy denial

Use the valid golden input and inject a deterministic policy result:

```json
{
  "result": "deny",
  "policyId": "panda.v0.1.filesystem-write",
  "reason": "phase-0 acceptance denial"
}
```

The transition to Action may be accepted, but the required policy evaluation
immediately before the external effect denies execution. Action returns a
structured rejected outcome. The connector is not invoked. Decision evaluates
the denial and terminates failed because the v0.1 fixture has no authorized
alternative. The trace contains both the denial and the resulting decision;
neither is represented as success.

Sandbox-violation and unsupported-action denials are additional Phase 5 unit
fixtures. This injected denial is the end-to-end policy fixture because it
isolates policy behavior from Analysis path validation.

### 4.3 Connector failure

Use the valid golden input and an injected filesystem connector that returns a
structured failure before writing any bytes. The attempt counts as a connector
invocation, but no effect completes and no verification observation is
fabricated. Action exposes the failure to Decision, which records the lack of
a safe v0.1 recovery and terminates failed. The goal remains unachieved and the
sandbox contains no `proof.txt` created by the execution.

### 4.4 Verification failure

Use the valid golden input. The connector returns a completed outcome, after
which the independent Perception operation supplies observed content
`PANDA v0.1 mismatch`. Analysis records the byte/hash mismatch against the
goal. Decision terminates failed with verification evidence. A successful
action outcome remains in the trace but cannot override the failed
environmental verification or achieve the goal.

## 5. Sandbox and allowed effect

The v0.1 sandbox root for one execution is:

```text
.panda/runs/<executionId>/workspace
```

The root is resolved from a runtime-configured PANDA data directory; tests use
a temporary directory and must not write to the repository checkout. The
execution ID is validated as an identifier, not interpolated as an arbitrary
path.

The sole allowed external effect type is `filesystem.write` through the
filesystem Action connector. It may create or replace one regular file below
the current execution's workspace. Before the effect, policy and connector
boundary validation must reject:

- absolute paths;
- empty paths and paths that resolve to the workspace root;
- traversal through `..`;
- symlink or equivalent filesystem escapes;
- targets outside the current execution workspace;
- unsupported action types;
- content larger than the runtime's declared v0.1 maximum.

The content-size maximum is a runtime configuration decision made in Phase 5.
Its value must be inspectable and the oversized-content test uses one byte more
than that configured value. No network, process, repository, or unrestricted
filesystem mutation is allowed by the v0.1 profile.

## 6. Scenario status and failure rules

- Only verified matching environmental state produces execution
  `succeeded` and goal `achieved`.
- Missing required information produces execution `waiting` and goal
  `awaiting-human`; it is resumable and not terminal.
- Policy denial, connector failure, and verification mismatch produce a
  structured failure, a final Decision, execution `failed`, and goal `failed`
  for the deterministic fixtures.
- Cancellation and invocation/deadline limits terminate with their explicit
  outcomes when later phases exercise them; they must not be converted to
  success.
- Unknown or partial effects remain unknown or partial. They are not treated as
  completed effects or verified goal success.

## 7. Trace contract

The execution trace is append-only and causally navigable. It contains the
following categories when applicable:

- signal acceptance;
- goal creation and status changes;
- capability invocation start and completion;
- observation creation;
- assessment creation, including evidence and information needs;
- decision creation, including alternatives, rationale, and decisive evidence;
- transition request, policy result, and committed or rejected transition;
- action request and connector invocation;
- action outcome;
- effect-verification observation and assessment;
- structured failure;
- wait or termination.

Every material record contains or inherits:

- stable `id`;
- `schemaVersion`;
- `executionId`;
- `goalId`;
- `correlationId`;
- optional `causationId`, absent only where the record is a causal root;
- producing capability or named runtime component;
- timestamp;
- record category/type;
- typed payload, result, or typed reference to it.

Phase 2 assigns a monotonic sequence number within each execution. Every
non-root material record references an earlier record in the same execution as
its direct cause. Cross-execution causation is invalid. Timestamps and sequence
order must not be used as substitutes for causation.

The trace must let an operator determine what entered the system, which route
was selected, why the action was or was not authorized, what was attempted,
what outcome occurred, what environmental effect was observed, and why the
goal reached its current status. Structured evidence and rationale satisfy
this requirement; hidden model chain-of-thought is neither required nor
recorded.

## 8. Persistence and restart behavior

The v0.1 execution and trace store is in-memory. It isolates concurrent
executions while the process is running but provides no durability across
daemon or process restart. A restart may lose execution state, goal state, and
trace records. PANDA v0.1 does not claim recovery, replay, exactly-once
delivery, or production durability.

Filesystem effects already completed inside a sandbox may outlive the
in-memory record. Their presence after restart does not recreate or imply a
verified execution. Durable execution recovery is deferred beyond v0.1.

## 9. Release-test acceptance

Phase 0 is considered implemented when later tests can be written directly
from this document. PANDA v0.1 release acceptance ultimately requires:

1. The golden fixture reaches verified success with the exact route and file.
2. Missing information waits with no action request or connector invocation.
3. Policy denial invokes no connector and cannot appear as success.
4. Connector failure completes no effect and cannot achieve the goal.
5. Verification mismatch fails despite a completed action outcome.
6. Every fixture preserves execution, goal, correlation, and valid same-
   execution causation identity.
7. Concurrent executions do not share active capability, goal, sandbox, or
   trace state.
8. Invocation limits stop unbounded routing explicitly.
9. All behavior works with deterministic implementations and no LLM.

## 10. Explicitly deferred work

The Phase 0 freeze does not add production behavior. Canonical TypeScript
contracts begin in Phase 1. Execution storage, coordination, deterministic
capabilities, policy, effects, verification, APIs, dashboard, legacy removal,
and release hardening remain ordered as specified in the
[v0.1 implementation plan](v0.1-implementation-plan.md).

Distributed infrastructure, durable brokers, production authentication,
general retries, multi-agent collaboration, model integrations, plugin
marketplaces, and production restart recovery remain v0.1 non-goals.
